# NetworkUSB — глубокий аудит и дополнительные сценарии применения

> Аналитический документ по состоянию репозитория на `2026-08-13`.
> Проверяемая ревизия: `4ff9411` (`arena/019ff9bf-networkusb`).
> Документ описывает **текущее поведение кода**, возможные сценарии и условия, при
> которых сценарий можно считать готовым к эксплуатации. Предложения ниже не
> означают, что соответствующая функция уже реализована.

## 1. Краткий вывод

NetworkUSB — это не универсальный «USB-over-IP». Утилита проксирует **локальный
UNIX-сокет `usbmuxd`** между двумя машинами:

```text
iPhone ── USB ── Mac с агентом ── TCP/TLS ── Mac с bridge ── UNIX socket ── клиент
```

Поэтому её сильная сторона — прозрачная поддержка программ, которые уже умеют
работать с `usbmuxd` и позволяют указать альтернативный локальный сокет. Это
позволяет вынести физическое подключение iPhone на отдельную машину, не меняя
диагностическое или автоматизационное ПО.

Наиболее перспективные направления:

1. удалённая первая линия диагностики и сервисная поддержка;
2. централизованный плановый health-check парка iPhone;
3. hardware-in-the-loop в CI и автоматизированные QA-стенды;
4. распределённая «ферма» устройств с выдачей устройств по UDID;
5. удалённый сбор логов, диагностических данных и резервных копий;
6. zero-touch развёртывание удалённых клиентских Mac через Tailscale;
7. экспериментальное удалённое iOS-разработческое окружение.

Главное ограничение перед production — не шифрование как таковое, а отсутствие
защит вокруг транспортного слоя: лимитов ресурсов, изоляции медленных сессий,
полного управления секретами и законченного installer/menu-bar workflow. Для
одной доверенной пары Mac прототип уже функционален; для нескольких операторов,
устройств или нестабильной WAN-сети нужен этап hardening.

## 3. Фактическая модель работы

### 3.1. Agent

`usbmuxd-agent` на Mac, к которому подключён iPhone:

1. открывает TLS-сервер, по умолчанию на `0.0.0.0:8721`;
2. принимает строку `AUTH <token>`;
3. после успешной аутентификации принимает бинарные фреймы;
4. на каждый `CONNECT` открывает отдельное соединение к локальному
   `/var/run/usbmuxd`;
5. передаёт байты между этим соединением и bridge;
6. закрывает сессии при `CLOSE`, EOF или ошибке.

Код находится в `src/networkusb/agent/server.py` и
`src/networkusb/agent/main.py`.

### 3.2. Bridge

`usbmuxd-bridge` на мастер-машине:

1. устанавливает TCP+TLS-соединение с agent;
2. проверяет fingerprint сертификата;
3. отправляет токен после проверки сертификата;
4. создаёт локальный UNIX-сокет, например `/tmp/usbmuxd.sock`;
5. на каждое локальное соединение создаёт multiplexed-сессию;
6. после разрыва удалённого соединения удаляет локальный сокет и пытается
   подключиться снова с backoff.

Код находится в `src/networkusb/bridge/client.py` и
`src/networkusb/bridge/main.py`.

### 3.3. Протокол

Фрейм имеет формат:

| Размер | Поле | Назначение |
|---:|---|---|
| 1 байт | `msg_type` | `CONNECT`, `DATA`, `CLOSE`, `HEARTBEAT` |
| 4 байта | `session_id` | uint32, идентификатор сессии |
| 4 байта | `payload_len` | длина полезной нагрузки |
| N байт | `payload` | сырые байты `usbmuxd` |

Таким образом, NetworkUSB не разбирает команды iOS, не выбирает устройство по
UDID и не знает, является ли трафик lockdown, AFC, syslog, developer services
или другим сервисом. Это полезно для совместимости, но означает, что политика
доступа должна строиться вокруг agent/bridge, а не внутри утилиты.

### 3.4. Границы применимости

**Работает или потенциально работает:** любой клиент, который действительно
использует локальный `usbmuxd` и принимает альтернативный путь к UNIX-сокету.
В репозитории зафиксированы `pymobiledevice3`, `iScan` и команды уровня
`usbmuxd`/`lockdown`.

**Не следует считать поддержанным без отдельного PoC:** Xcode, Apple
Configurator, WDA/Appium, инструменты, использующие дополнительные системные
каналы, а также программы, жёстко зашитые на `/var/run/usbmuxd`.

**Не покрывается:** произвольные USB-устройства, Android, USB storage/HID,
DFU/recovery-режимы, полноценный USB-over-IP и общий TCP-прокси. В DFU или
recovery `usbmuxd` обычно не является доступным транспортом, поэтому этот
туннель не заменяет инструменты восстановления устройства.

## 5. Дополнительные сценарии применения

### 5.1. Удалённая первая линия поддержки

**Идея.** Клиент подключает iPhone к локальному Mac в магазине или сервисном
пункте, а инженер на центральном Mac запускает `pymobiledevice3`, `iScan` или
собственные диагностические команды.

**Рабочий поток:**

1. На Mac клиента постоянно работает agent.
2. Tailscale или приватная сеть доставляет трафик только до мастер-машины.
3. Инженер поднимает отдельный bridge для конкретной точки.
4. Проверяет `usbmux list`, UDID, модель и версию iOS.
5. Запускает ограниченный набор диагностик и сохраняет результат в тикет.
6. После закрытия обращения bridge останавливается или остаётся в режиме
   ожидания.

**Преимущество:** оператору не нужно пересылать iPhone, а существующие
инструменты не требуют специального remote API.

**Условия:** pairing и нажатие «Доверять» должны быть выполнены локально;
токен и fingerprint должны передаваться отдельным защищённым каналом;
оператору нужно явно сообщить, какие персональные данные могут попасть в
отчёт. Общий token для всех магазинов использовать нельзя.

### 5.2. Плановый fleet health-check

**Идея.** Центральный scheduler периодически опрашивает десятки удалённых
Mac и собирает единый реестр состояния устройств:

- виден ли agent и bridge;
- появился ли iPhone по USB;
- UDID, модель, iOS и имя устройства;
- результат `lockdown`/базовой диагностики;
- дата последнего успешного опроса;
- время round-trip и количество ошибок.

**Рекомендуемая схема:** один уникальный agent на рабочую станцию, один
короткоживущий bridge на job. Для каждой станции нужны отдельные:

- Tailscale hostname или разрешённый сетевой адрес;
- token-file;
- ожидаемый TLS fingerprint;
- локальный socket path;
- запись inventory с UDID и ответственным подразделением.

**Что добавить до внедрения:** health/readiness-команду, машинно-читаемый
статус, лимит одновременных опросов и метрики reconnect. Текущий `active.json`
не является fleet registry: он один на домашнего пользователя и может быть
перезаписан несколькими bridge.

### 5.3. Hardware-in-the-loop в CI

**Идея.** Mac mini с физическим iPhone становится тестовым bench, а CI-runner
на центральной машине запускает существующие тесты через локальный socket bridge.

**Жизненный цикл CI job:**

1. Получить эксклюзивную аренду bench по UDID.
2. Установить ожидаемый fingerprint и token-file из secret store CI.
3. Поднять bridge с уникальным socket path job-а.
4. Выполнить `usbmux list` и короткий smoke-test до запуска тестов.
5. Запустить тесты приложения или инструменты автоматизации.
6. Собрать логи и артефакты.
7. Закрыть bridge и освободить устройство даже при падении job-а.

**Почему это полезно:** не нужно переносить устройство к каждому runner-у и не
нужно переписывать инструменты, которые уже используют `usbmuxd`.

**Риски:** текущая реализация не гарантирует изоляцию медленной сессии от
других сессий; reconnect закрывает активные локальные соединения; latency WAN
может ломать тайминги developer services. Начинать следует с одного bench в
приватной сети, не с общей публичной фермы.

### 5.4. Удалённый QA и smoke-тестирование приложений

Через совместимый с `usbmuxd` стек можно потенциально автоматизировать:

- установку тестовой сборки;
- запуск приложения;
- получение базовой информации о системе;
- сбор диагностических логов;
- проверку developer services;
- выполнение короткого сценария после подключения устройства.

Для iOS 17+ в проекте отдельно отмечен `pymobiledevice3 remote start-tunnel`.
Это означает, что NetworkUSB может быть транспортным нижним уровнем, но не
заменяет настройку iOS developer tunnel. Для Appium/WDA и похожих стеков нужно
проверить именно используемые ими lockdown/developer-соединения — одной успешной
команды `usbmux list` недостаточно.

### 5.5. Удалённый сбор логов и диагностических данных

**Идея.** Сервисный Mac с телефоном остаётся на объекте, а центральный инженер
получает логи и диагностические артефакты без физического доступа к устройству.
Это может включать syslog, сведения lockdown, диагностические сервисы и
резервное копирование через совместимые клиентские инструменты.

**Особое внимание:** такой сценарий часто раскрывает имя владельца, сообщения,
фотографии, идентификаторы и другие персональные данные. Нужны:

- явное согласие и понятное описание сбора;
- шифрование и контроль доступа к файлам на мастер-машине;
- срок хранения и автоматическое удаление;
- журнал того, кто запускал экспорт;
- запрет использования общего token несколькими операторами.

Транспортное TLS-шифрование само по себе не решает проблему защиты данных
после их получения на master.

### 5.6. Device farm с выдачей устройств по UDID

NetworkUSB можно использовать как низкоуровневый слой для фермы:

```text
orchestrator ── lease ──> bench-01/agent + bridge-01 ──> iPhone A
             ── lease ──> bench-02/agent + bridge-02 ──> iPhone B
```

Оркестратор должен хранить состояние устройства, выбирать bridge, блокировать
параллельные job-ы и возвращать устройство в quarantine при ошибке.

Код `AgentServer` допускает несколько bridge-подключений, а протокол допускает
много сессий, но это не равно готовой multi-tenant ферме: лимитов и ACL нет,
параллельная работа одного iPhone не тестировалась, а устройства не выбираются
самой NetworkUSB. Практический первый вариант — один агент/bridge на один bench
и один lease за раз.

### 5.7. Zero-touch подключение удалённых рабочих мест

Клиентский `.pkg` уже задуман как средство для нетехнического оператора:
Tailscale, Python, venv, token-file и LaunchDaemon устанавливаются после одного
запуска Installer.

Это подходит для:

- магазинов без локального инженера;
- сервисных точек в разных городах;
- временных выездных стендов;
- пилотного подключения нового Mac к central master.

Безопасный процесс выдачи:

1. генерировать отдельный одноразовый Tailscale auth key на каждый пакет;
2. ограничивать его срок и ACL в tailnet;
3. после установки удалить или отозвать ключ;
4. получить token агента по отдельному защищённому каналу;
5. получить fingerprint и внести его в конфигурацию bridge;
6. не вкладывать постоянный NetworkUSB token в пакет или общий чат;
7. после эксплуатации удалить клиентскую машину из tailnet и отозвать token.

Сейчас этот сценарий не следует считать полностью готовым: clean checkout не
содержит `installer/third_party/tailscaled`, GitHub workflow не загружает эти
бинарники, `.pkg` не подписывается/notarизуется, а конфигурация menu-bar не
генерируется автоматически.

### 5.8. Удалённая iOS-разработка и отладка

Можно исследовать использование туннеля для удалённого запуска некоторых
developer services, отладки и интеграционных тестов. Это привлекательный
сценарий для команды, где устройства находятся в лаборатории, а разработчики —
в другом офисе.

Однако его нужно маркировать как **экспериментальный**:

- Xcode может использовать дополнительные сервисы и собственные ожидания по
  локальному подключению;
- pairing/developer image и iOS 17+ remote tunnel добавляют состояния, которые
  текущий протокол не моделирует;
- latency и потеря пакетов влияют на LLDB и интерактивные операции;
- один медленный поток сейчас может задержать обработку остальных сессий.

Сначала нужен отдельный PoC на конкретных версиях macOS, Xcode и iOS, затем
регрессионные тесты на reconnect и sleep/wake устройства.

### 5.9. Централизованный учебный или лабораторный стенд

В учебной лаборатории преподаватель может давать доступ к нескольким тестовым
iPhone с центрального Mac, не перенося устройства между рабочими местами.
Каждой группе следует выдавать свой bridge endpoint и отдельный token, а доступ
к приватному UNIX-сокету ограничивать владельцем процесса.

Это хороший сценарий для демонстрации диагностики и сетевого multiplexing, но
не для реальных пользовательских данных. Лабораторные телефоны должны быть
очищены, не привязаны к личным Apple ID и работать в отдельном tailnet.

## 6. Сценарии, для которых NetworkUSB не подходит

| Сценарий | Причина |
|---|---|
| Произвольное USB-over-IP | Передаются сессии `usbmuxd`, а не USB-транзакции и не USB-классы |
| Android, флешки, камеры, HID, serial USB | Эти устройства не обслуживаются локальным `usbmuxd` |
| DFU/recovery/firmware restore как единственный транспорт | В этих режимах обычный `usbmuxd` может отсутствовать |
| Публичный Internet endpoint без VPN/ACL | Есть shared token, нет per-client authorization и полноценного rate limit |
| Общая SaaS multi-tenant ферма | Нет аренды, quota, identity оператора и изоляции сессий |
| Гарантированная поддержка Xcode/Appium | Нужна проверка дополнительных developer-сервисов |
| Неконтролируемые bulk-передачи через перегруженную WAN | Нет per-session queue и защиты от head-of-line blocking |
| Высоконадежный audit/forensics без доработок | Нет полного журнала действий и встроенной политики хранения данных |

## 7. Результаты аудита реализации

### 7.1. Что сделано хорошо

- Ясное разделение agent/bridge и минимальный бинарный протокол.
- `read_frame` ограничивает размер входного payload 4 MiB.
- Есть TLS 1.2+ и SHA-256 fingerprint.
- В текущем коде `expected_fingerprint` проверяется **до** отправки AUTH.
- Сравнение token в agent выполняется через `secrets.compare_digest`.
- Поддерживается `--token-file`, а default socket mode в CLI — `0700`.
- Reconnect и безопасный shutdown покрыты интеграционными тестами.
- `SessionIdAllocator` учитывает uint32 wrap-around.
- Запись сертификатов и `known_hosts` использует временный файл и `os.replace`.
- Есть реальный end-to-end тест: local UNIX client → bridge → TLS → agent →
  mock `usbmuxd` → обратно.
- Installer генерирует постоянный NetworkUSB token на клиентской машине, а не
  кладёт его в исходный код проекта.

### 7.2. Наиболее важные открытые риски

#### AUDIT-01 — head-of-line blocking между сессиями (High)

В `bridge/client.py` reader loop последовательно пишет полученные данные в
локальный writer и ждёт `local_writer.drain()`. В `agent/server.py` центральный
dispatch loop аналогично ждёт `sess.writer.drain()` при записи в локальный
`usbmuxd`.

Один клиент, который перестал читать, может задержать DATA, CLOSE и heartbeat
для других сессий. Это особенно опасно для device farm и интерактивного
lockdown/LLDB-трафика.

**Рекомендация:** bounded queue и отдельная writer task на сессию с приоритетом
control-фреймов; при переполнении закрывать только проблемную сессию.

#### AUDIT-02 — недостаток лимитов и таймаутов (High)

Не видно конфигурируемых лимитов для числа bridge, TLS/auth подключений и
сессий. `CONNECT` открывает UNIX-соединение без отдельного timeout; DATA и
чтение фреймов также не имеют idle/deadline-политики. Ограничение 4 MiB на один
фрейм не является общим budget очередей.

**Риск:** slowloris, исчерпание файловых дескрипторов/памяти и зависание
центрального dispatch loop.

**Рекомендация:** лимиты bridge/session, handshake/auth/frame timeout, rate
limit неуспешного AUTH, общий и per-session byte budget.

#### AUDIT-03 — безопасный bootstrap TLS не является обязательным (High)

CLI поддерживает `--expected-fingerprint`, но по умолчанию используется TOFU:
первый сертификат автоматически сохраняется. В menu-bar `startBridge()`
передаёт только host, port и token, не передаёт expected fingerprint. TLS client
context намеренно использует `CERT_NONE`, поэтому безопасность полностью зависит
от корректного pinning/канала первого обмена.

Agent также слушает `0.0.0.0` по умолчанию. Tailscale снижает сетевой охват, но
не заменяет bind на нужный интерфейс и firewall ACL.

**Рекомендация:** в production требовать fingerprint или доверенный CA,
добавить его в config/menu-bar, показывать явное подтверждение при TOFU и
ограничивать listen address/firewall tailnet-адресом.

#### AUDIT-04 — секрет попадает в config и аргументы процесса (High)

Swift-модель `Config` содержит открытое поле `token`, а `startBridge()` запускает
процесс с `--token`. Это оставляет секрет в JSON и потенциально в списке
процессов. `resolve_token()` для слишком либеральных прав token-file только
пишет warning, а не отказывает в запуске.

**Рекомендация:** передавать token только через root/user-owned `0600`
 token-file или защищённый IPC/Keychain, не хранить его в menu config, сделать
проверку прав обязательной для production-профиля и добавить ротацию/revocation.

#### AUDIT-05 — clean CI build installer не воспроизводится (High)

`installer/build_client_pkg.sh` требует исполняемые
`installer/third_party/tailscaled/arm64/tailscaled` и `amd64/tailscaled`. В
текущем checkout этой директории нет, а `.gitignore` исключает весь
`installer/third_party/`. GitHub workflow делает только checkout и сразу
запускает build; шага скачивания или проверки checksum для tailscaled нет.

Дополнительно:

- `uv` скачивается с `releases/latest`, без фиксации версии и checksum;
- зависимости Python заданы нижними границами, а не lock-файлом;
- пакет unsigned/notarization отсутствует;
- auth key Tailscale встраивается в сгенерированный postinstall и должен
  считаться секретом до первого использования.

**Рекомендация:** определить источник и версию ассетов, фиксировать SHA-256,
проверять подписи, сделать clean checkout build частью CI и подписывать/notarize
`.pkg`.

#### AUDIT-06 — menu-bar workflow расходится с CLI (High)

В `Config` есть `socket_path`, но `startBridge()` не передаёт `--socket-path`.
Bridge в таком случае создаёт default `/tmp/usbmuxd.sock`, тогда как проверки
устройств и `getInfo()` используют `cfg.socket_path`. Любой custom socket path
может привести к тому, что menu-bar смотрит не на тот endpoint.

В репозитории также нет Xcode-проекта/Swift Package для сборки
`NetworkUSBMenu.app`, нет schema/example для
`~/.config/usbmuxd-bridge/config.json`, а `scripts/nusb` ожидает уже
установленное приложение в `~/Applications`.

**Рекомендация:** сделать единый конфиг, передавать из него все параметры CLI,
добавить пример и валидатор конфигурации, собрать menu-bar app в отдельный
артефакт installer/CI.

#### AUDIT-07 — небезопасное управление локальным socket path (Medium/High)

Default `/tmp/usbmuxd.sock` предсказуем. `_start_unix_server()` удаляет
существующий путь по имени без проверки типа/владельца; `_teardown()` аналогично
удаляет путь. `scripts/nusb stop` дополнительно делает `rm -f` и использует
широкий `pkill -f`.

**Рекомендация:** приватный runtime directory mode `0700`, socket mode `0600`,
проверка `lstat`/типа/владельца, отказ при неожиданном stale path, PID-aware
управление процессами и уникальный socket path для каждого job.

#### AUDIT-08 — неполная валидация протокола (Medium)

`build_frame()` проверяет диапазон `session_id`, но не запрещает payload больше
`MAX_PAYLOAD_SIZE` и не проверяет, что у control-фреймов payload пустой. В
dispatch нет защиты от duplicate `CONNECT` с тем же ID, нет строгой проверки
`HEARTBEAT` с `session_id == 0` и нет отдельной политики для flood DATA/CLOSE
неизвестной сессии.

**Рекомендация:** единый validator фреймов на обеих сторонах, строгая state
machine сессии и тесты на malformed/duplicate/control frames.

#### AUDIT-09 — жизненный цикл сертификатов и known_hosts требует locking (Medium)

`os.replace` защищает от частично записанного отдельного файла, но две
параллельные генерации могут конкурировать за пару cert/key, а параллельные
bridge могут потерять обновление `known_hosts` при read-modify-write без
межпроцессной блокировки. Срок self-signed сертификата около 10 лет, механизма
плановой ротации и автоматического обновления pin нет.

**Рекомендация:** lock на директорию/known_hosts, fsync, проверка соответствия
сертификата ключу, короткая документированная ротация и явная процедура
обновления fingerprint.

#### AUDIT-10 — стартовая проверка usbmuxd недостаточно точна (Medium)

`agent/main.py` проверяет `os.path.exists(usbmuxd_path)`, хотя в `utils.py` уже
есть `check_unix_socket_accessible()`. Регулярный файл или недоступный UNIX
socket может пройти preflight, а ошибка появится только на первом `CONNECT`.

**Рекомендация:** проверять `stat.S_ISSOCK`, права и короткое тестовое
подключение; для LaunchDaemon использовать понятный retry до появления
`usbmuxd`.

#### AUDIT-11 — operational state и observability недостаточны (Medium)

Есть `active.json`, но он один на пользователя и не рассчитан на несколько
bridge. Нет отдельного health endpoint, counters, длительности сессий,
пропускной способности и причины последнего reconnect. Heartbeat проверяется
на agent, а bridge не имеет полноценного timeout ответа на heartbeat.

**Рекомендация:** добавить `status/health`, JSON-логи без секретов, метрики
active sessions/reconnect/bytes/errors и state machine для bridge.

#### AUDIT-12 — документация и security policy устарели относительно кода (Medium)

`PROBLEMS.md` одновременно перечисляет исправленные F-02/F-03/F-04/F-09/F-10/F-11
как закрытые в summary и как открытые в подробных секциях. Файл прямо указывает
на более старую базу `783b15e`.

Другие расхождения:

- `SECURITY.md` заявляет обязательный TLS 1.3, а код задаёт minimum TLS 1.2;
- security policy говорит о pre-auth fingerprint verification, но default CLI
  всё ещё допускает автоматический TOFU;
- README называет ограничение «один Bridge на агента», хотя `AgentServer`
  хранит несколько bridge tasks и принимает несколько соединений;
- README/комментарии местами упоминают `0777`, хотя default уже `0700`;
- installer docs говорят о готовом config JSON, но schema и генератора в repo
  нет.

**Рекомендация:** обновлять аудит в той же ревизии, что и fixes, и ввести CI
проверку ссылок/примеров CLI.

## 8. Безопасный базовый профиль эксплуатации

До исправления перечисленных проблем минимальный профиль должен выглядеть так:

1. Использовать только приватную сеть или tailnet, не публиковать порт `8721` в
   Internet.
2. Для agent ограничить bind/firewall разрешёнными адресами master.
3. На каждую рабочую станцию генерировать отдельный token длиной не менее 32
   случайных байт.
4. Хранить token в `root:wheel`, mode `0600`; не использовать `--token` в
   production и не класть token в menu config.
5. Получать fingerprint из доверенного канала и задавать
   `--expected-fingerprint`; не полагаться на молчаливый TOFU.
6. Создавать отдельную директорию socket-а mode `0700` и уникальный socket path
   для каждого master/job.
7. Не запускать параллельные job-ы на одном iPhone.
8. Считать все backup/log/diagnostic артефакты персональными данными.
9. Ограничить lifetime bridge и удалять lease/token после временного стенда.
10. Проверять `usbmux list` и короткий round-trip перед каждым сложным сценарием.

Пример ручного запуска без передачи постоянного token в командной строке:

```bash
# master
mkdir -p "$HOME/.config/networkusb" "$HOME/.local/run/networkusb"
chmod 700 "$HOME/.config/networkusb" "$HOME/.local/run/networkusb"

usbmuxd-bridge \
  --agent-host 100.x.y.z \
  --agent-port 8721 \
  --token-file "$HOME/.config/networkusb/site-01.token" \
  --expected-fingerprint 'AA:BB:CC:...' \
  --socket-path "$HOME/.local/run/networkusb/site-01.sock" \
  --socket-mode 0600

export USBMUXD_SOCKET_ADDRESS="$HOME/.local/run/networkusb/site-01.sock"
pymobiledevice3 usbmux list
```

Перед реальным применением нужно дополнительно проверить, какой формат
`USBMUXD_SOCKET_ADDRESS` ожидает конкретная версия клиентской библиотеки;
README содержит варианты с `unix:` и без него.

## 9. Приоритетный roadmap

### P0 — до нескольких production-стендов

1. Реализовать per-session queues/writer tasks и тест на медленный consumer.
2. Ввести max bridges, max sessions, handshake/auth/connect/frame timeouts и
   byte budgets.
3. Убрать token из menu config/process args; сделать strict token-file.
4. Сделать expected fingerprint обязательным для production/menu-bar пути.
5. Исправить clean installer build: third-party assets, версии, checksum,
   подпись/notarization.
6. Исправить передачу `socket_path` в menu-bar и добавить config schema/example.

### P1 — надёжность и безопасность

1. Строгая state machine и валидация фреймов.
2. Безопасный runtime directory и PID-aware stop/reconnect.
3. Lock и ротация cert/known_hosts.
4. Проверка реального UNIX socket вместо `exists()`.
5. Тесты на auth failures, malformed frames, duplicate IDs, concurrency,
   half-open TCP, reconnect с активными сессиями и большой one-way поток.
6. CI для pytest/mypy/ruff и отдельно для macOS installer/menu-bar.
7. Синхронизация `README.md`, `PROBLEMS.md` и `SECURITY.md` с текущим кодом.

### P2 — продуктовые возможности

1. `usbmuxd-agent status`/health и JSON metrics.
2. Per-agent/per-operator identities вместо одного shared token.
3. API или CLI для device inventory и lease.
4. Ротация token/fingerprint без остановки всех стендов.
5. Автоматизация iOS 17+ remote tunnel.
6. Официальные инструкции и PoC для Appium/WDA/Xcode.
7. Поддержка Linux gateway только после явного решения о cross-platform scope.

## 10. Критерии готовности для сценариев

Сценарий можно переводить из PoC в production только после подтверждения:

- повторяемый clean install на macOS 13+ для arm64 и x86_64;
- сборка `.pkg` из чистого checkout с проверенными third-party checksum;
- подписанный и notarized installer;
- strict fingerprint/token-file path без секретов в процессах и логах;
- тест 100 MiB one-way и два параллельных потока, где slow consumer не
  блокирует интерактивный поток;
- лимиты и понятные ошибки при превышении quota;
- reconnect после agent restart, sleep/wake и временной потери tailnet;
- pairing, `usbmux list`, lockdown и целевой инструмент проверены на реальном
  iPhone;
- cleanup socket/lease выполняется после успешной и аварийной job;
- для backup/log use case утверждены consent, retention и access audit;
- для device farm один job не может одновременно получить один UDID дважды.

## 11. Итоговая рекомендация

Лучший первый продуктовый фокус — не позиционировать NetworkUSB как общий
удалённый USB, а как **защищённый транспорт для удалённых iOS-диагностических и
автоматизационных сервисов**.

Практический порядок внедрения:

1. remote service desk для одной-двух площадок;
2. плановый fleet health-check;
3. один CI bench с эксклюзивным lease;
4. затем device farm и удалённые QA-сценарии.

Эти сценарии напрямую используют уже существующую архитектуру. Xcode,
мультиарендность, публичный доступ и высоконагруженные backup-потоки лучше
оставлять за пределами обещаний до закрытия P0/P1 из аудита.
